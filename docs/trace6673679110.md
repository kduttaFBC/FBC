## Where it diverges from the business rules

1. **A genuine full-P&I deferral is silently discarded — `checks.py:1068` (highest impact).** Row 49's Jan–Mar 2026 full-P&I deferral is filed under `Securitization Action = "Modification"`; the `== "deferred"` filter drops it with no warning. For any audit cycle in that window, STAT-01 does not set Loan Status = DEFERRED and runs normal delinquency math on a loan that was in a payment freeze — a direct divergence from the rule "full P&I deferral → freeze / +1 and Loan Status DEFERRED." The filter is a *deliberate* choice (comment 1060–1066) to reject Change-Memo rows that copy deferral dates, and that rationale is sound — but the filter cannot distinguish a mislabeled real deferral from noise, and it fails silently.

> **Proposed investigation outcome (not an approved fix).** If a dropped non-`Deferred` row contains all of: internally-consistent deferral dates, full-P&I Servicer Action text, and overlap with the audit cycle — classify it as a data-quality conflict requiring reviewer attention rather than silently excluding it. **Do not automatically treat it as Deferred without confirming the intended business rule** — the safe move is to expose the conflict for a human, not to assert the deferral. (Scope first: count how many other loans hit this before deciding how far the rule should reach.)

2. **The rolling deferral is fragmented as a consequence.** Because row 49 is gone, the Apr-2026 boundary (Resume A = Start B) never arises; STAT-01 sees only Deferral B starting April. The loan's real Jan→Jul continuity becomes: Jan–Mar normal math (wrong), Apr–Jun deferred, Jul resume. This is a downstream effect of #1, not a separate bug — but it means the `prior_missed` the ladder carries into April (SOUP's March value) may itself already be wrong.

3. **`deferral_type` defaults to `full` when ambiguous (file_readers 84–97) — latent, not triggered here.** Both rows are genuinely full, so no misclassification for this loan. But the default confirms the brief's concern: an ambiguous Servicer Action becomes `full`, which is the direction that *enables* an auto Loan-Status→DEFERRED write (corrections.py gates on `deferral_type == "full"`). A truly-partial deferral phrased ambiguously (e.g. "deferment of principal paying interest") would slip through as full. Worth hardening even though this loan doesn't hit it.

4. **Stale in-code documentation (minor).** The module comment at lines 830–833 still describes the `start` cycle as a FREEZE that "holds" the rank; the implemented, client-confirmed behavior (lines 1394–1420) advances `+1` on the start cycle too. Code is correct per the latest confirmation; the comment is stale and should be reconciled so a future reader doesn't "fix" the code back to the old rule.

**Not diverging:** ID keying (normalized correctly, both `gp_sba`/`gp_lender` tried, alias resolves), the deferral dates (clean, internally consistent — no date-order anomaly on this loan), `deferral_type` value, the resume reset (implemented and client-confirmed), and `report.py` (faithful).
